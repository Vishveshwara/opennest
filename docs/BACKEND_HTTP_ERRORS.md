# OpenNest HTTP errors and security baseline

Phase 1.7 added Spring MVC, Jakarta validation, common Problem Details, and restrictive security. Phase 2 reuses this contract for enabled Google OIDC and Redis sessions; see the [identity handoff](IDENTITY_HANDOFF.md). Disabled Google retains the baseline. Demo authentication, public health endpoints, and diagnostic APIs remain unavailable. Error rendering preserves validated CORS response headers for the configured frontend.

## Response contract

Handled errors return `application/problem+json`, including requests that prefer HTML. Every body has exactly these five fields:

```json
{
  "type": "about:blank",
  "title": "Internal Server Error",
  "status": 500,
  "detail": "An unexpected error occurred.",
  "instance": "urn:uuid:4d61759a-27b6-4a52-a830-56b2691c64a2"
}
```

The UUID is generated by the server for each error. `X-Error-Id` repeats that UUID for log correlation. The body never copies the request path/query, caller IDs, exception messages, rejected values, validation messages, SQL, contacts, credentials, or tokens. Incoming error-ID headers are ignored. An existing uncommitted response is reset to remove partial output and private headers before writing the problem.

| Status | Fixed detail |
| --- | --- |
| 400 | The request is invalid. |
| 401 | Authentication is required. |
| 403 | Access is denied. |
| 404 | The requested resource was not found. |
| 408 | The request timed out. |
| 409 | The request conflicts with the current state. |
| 410 | The requested resource is no longer available. |
| 422 | The request could not be processed. |
| 429 | The request limit has been reached. |
| 503 | The service is temporarily unavailable. |
| 500 | An unexpected error occurred. |

The title is the standard HTTP reason phrase. Responses include `Cache-Control: no-store`, `X-Content-Type-Options: nosniff`, `X-Frame-Options: DENY`, and `Referrer-Policy: no-referrer`. Shared safeStatus preserves Spring's recognized 4xx statuses, including 408, 410, and 422. Other recognized client statuses use a fixed client-error detail; unsupported codes and unexpected server statuses become generic 500, while 503 is retained. A 405 retains the framework's supported-method Allow header. Retry-After is not invented without a known retry time.

The response uses Spring's [ProblemDetail representation](https://docs.spring.io/spring-framework/reference/web/webmvc/mvc-ann-rest-exceptions.html). A shared writer handles controller advice, Security entry/access-denied handlers, firewall rejections, a filter boundary, and servlet error dispatch. Direct JSON writing avoids HTML fallback and arbitrary exception-provided Problem Details extensions.

## Failure classification

`in.opennest.common.RequestFailure` is common's first public Java contract. Its fixed Kind enum expresses invalid input, unauthenticated, forbidden, missing, conflict, rate limit, or unavailable conditions. It accepts no arbitrary message/cause. Feature modules must declare their common dependency when they begin consuming this contract; no cross-module dependency is added now.

| Failure | Result |
| --- | --- |
| Malformed JSON, missing/incorrect parameters, body validation, request method validation | 400, without rejected values or validation text |
| Return-value validation or response-conversion failures | Generic 500, including any ConstraintViolationException path containing a RETURN_VALUE node |
| Empty/non-return ConstraintViolationException sets | 400 |
| Spring authentication/access-denied exceptions | Advice rethrows unchanged; Security selects 401 for authentication or anonymous access denial, 403 for authenticated access denial |
| Missing MVC resource and recognized HTTP status exceptions | Safe framework status; exception reason/body discarded |
| DuplicateKeyException, optimistic-lock exceptions, or recognized SQLSTATE 23505 through persistence/data-access wrappers | 409 |
| JDBC/Redis resource connection failures, query/SQL timeouts, recognized SQLSTATE class 08 | 503 |
| Generic integrity error, foreign-key/not-null violation, bad SQL/schema, unknown Redis/system error | Generic 500 |
| IllegalArgumentException, IllegalStateException, or other unexpected application exception | Generic 500, even if an arbitrary application wrapper contains a known conflict/outage cause |

Cause inspection unwraps recognized data-access, persistence, transaction, JDBC, and servlet wrappers only. It does not search messages or translate every database exception to 409/503. Recognizing a quota/conflict does not implement its transactional enforcement. Rate limiting, publication quotas, owner serialization, and review idempotency remain feature work.

## Security defaults

- Every normal request is denied, including requests with an injected authenticated principal. Anonymous requests receive 401; authenticated denied requests receive 403. An unsafe request without valid CSRF receives 403 before authorization. There are no public application route exceptions yet.
- Form login, HTTP Basic, logout processing, and saved-request caching are disabled. The AuthenticationManager rejects all authentication attempts. Its bean prevents Boot from creating a default password user; configuring spring.security.user does not create access. [Boot security configuration](https://docs.spring.io/spring-boot/reference/web/spring-security.html) documents that distinction.
- CSRF and standard Security headers remain enabled. This phase does not expose a CSRF-token endpoint or implement Google/server-session login. Framework CSRF state is not an authentication flow.
- Only trusted servlet ERROR dispatch bypasses request authorization to render the framework's internal `/error` fallback. A direct HTTP request to `/error` remains denied. The fallback reads only a recognized status; it discards error messages, exception objects, and request metadata.
- No actuator, demo-login provider, persona switch, or diagnostic business endpoint is added. Test-only controllers and a higher-priority test-only chain exist solely in test sources under `/api/v1/test-contract/...`; they are absent from the packaged application.

## Logging and configuration

HTTP logging emits the writer's fixed `OpenNest HTTP error status=<number> errorId=<UUID>` events at INFO for 4xx and ERROR for 5xx. Its logger threshold is INFO and additivity is disabled. Root logging permits ERROR events, including Spring Boot startup failure analysis, through a separate appender that prints timestamp, level, and the literal `OpenNest framework failure; diagnostic details redacted` marker. Its pattern omits messages, arguments, logger/thread names, MDC, structured fields, and throwable output. Operators can see that a framework/startup failure occurred; its potentially private analysis text and stack trace remain redacted. No separate private trace store is provided.

The deployment post-processor fixes this Logback configuration, disables debug/trace, suppresses framework error message/stack/binding/exception output, disables request-detail and Tomcat access logging, and rejects direct logging/error-policy overrides. Logging changes require an explicit code/configuration-policy change. Future services must use reviewed structured events; direct stdout, external provider/proxy logs, and separate operating-system logs are outside this backend logging policy.

A response already committed to the client cannot be replaced with a new Problem Detail. The boundary records only its fixed safe event and does not dump the exception. Disconnected-client writes cannot guarantee a complete JSON body. Invalid HTTP syntax rejected before application dispatch remains the servlet container's responsibility.

## Verification

With Java 25, run the unit/context/HTTP checks or include the existing real database profile:

```powershell
.\backend\mvnw.cmd -f backend/pom.xml clean verify
.\backend\mvnw.cmd -f backend/pom.xml -Pschema-integration clean verify
```

On 22 October 2026, the clean full build passed 114 unit/context/module tests, including 45 MVC contract tests and five real embedded-container tests, plus 49 PostgreSQL/PostGIS integration tests. All 163 tests passed with zero failures/errors/skips. Error tests use test-only controllers, not diagnostic production routes.

The suite checks every required status, known versus unexpected failures, malformed/validated input, CSRF, denial of Basic/login/privileged access, absence of a password user, firewall/filter failures, real servlet error dispatch, generic 500 responses, fixed body keys, safe headers, matching server-generated log IDs, and canary exclusion from responses/logs. Normal application handler mapping exposes only the framework error fallback. Database tests retain both modes' migrations, schema validation, round trips, and stale-write checks; their servers now use random HTTP ports.

Docker is unavailable locally, so database tests used isolated PostgreSQL 17.11/PostGIS 3.5.3 targets. Migrations and entity mappings are unchanged. CI, hosted deployment, Redis isolation, and feature authentication/authorization were not run or claimed. Build logs are under ignored `target/phase-1.7/`.

The initial 30 October run passed all 186 tests with real Docker/PostGIS/Redis. Review corrections now cover the previously missing return-value ConstraintViolationException case, preserve empty-set 400 behavior, verify Security delegation and shared status handling, and check log levels and redaction during real startup failure.
