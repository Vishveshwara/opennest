- Status: business routes below remain proposed; Phase 1.7 implements common HTTP errors/security only. Normal requests are denied; no login, business, or diagnostic endpoint exists. Trusted servlet ERROR dispatch alone can reach the framework /error fallback.
- Application REST APIs use `/api/v1`; Spring Security OIDC redirects use the framework paths listed below. Request/response details finalized with each phase.
- Phase 1.5 V1/V2 implement the storage contract in `docs/SCHEMA_CONTRACT.md`, verified on isolated databases; generated fields/ownership keys do not add endpoints or grant client writes. Account role USER permits both listing ownership and accommodation seeking; authorization follows authenticated IDs/ownership.
- Phase 1.6 adds internal mappings/Hibernate validation and ORM optimistic locking, without business endpoints/DTOs. Caller-version comparisons, unchanged-inventory version increments, publication gates/quotas, and review authorization/idempotency remain feature service work; `docs/BACKEND_PERSISTENCE.md`.
- Planned initial login: Spring Security `GET /oauth2/authorization/google` and `GET /login/oauth2/code/google` (framework routes outside /api/v1); backend will validate OIDC and rotate the server session. See `docs/AUTHENTICATION.md`.
- `GET /api/v1/auth/csrf`: synchronizer token for the initiating session, no-store; `POST /api/v1/auth/logout`: CSRF-protected session invalidation and cookie expiry, 204. Session cookies Secure in production, HttpOnly, host-only, SameSite=Lax.
- Deferred WhatsApp: no OTP, webhook, challenge, or polling routes enabled at initial launch; reject rather than accept client assertions of verification. Google login never marks a phone verified.
- `GET /api/v1/users/me`: authenticated profile and phone verification state; contact data restricted to the account owner; no-store; unauthenticated -> 401.
- `GET /api/v1/listings/search`: public; optional city/locality/category/flatRentalMode/status, minRent/maxRent, minBedrooms/maxBedrooms, minTotalRooms/maxTotalRooms, hasWifi/hasGym/hasSwimmingPool, maxSharingPerRoom, genderRoomAvailable, and geo filters; omitted city means nationwide. Responses omit owner phone, private address, and precise coordinates; map coordinates require a documented coarsened representation, otherwise omit them. Full contract: `docs/LISTING_SEARCH.md`.
- Pagination: page=0 by default, size=20 (1..50), page >= 0 and page*size <= 10000; response {items, page, size, totalElements, totalPages, hasNext, hasPrevious, sort}. Out-of-range valid pages return empty items with actual totals.
- Sort: NEWEST default, RENT_ASC, RENT_DESC, ROOMS_DESC (ENTIRE_FLAT NULL totals last), RATING_DESC (unrated last), DISTANCE_ASC (complete geo query required); every order uses id ASC as final tie-breaker. Reject arbitrary field names/directions.
- Filters combine with AND; city/locality are normalized exact matches. Bedrooms describe FLAT layout (0 = studio), available rooms describe vacancy; bedroom filters exclude PG_HOSTEL. Default status ACTIVE; explicit FULL_OCCUPIED allowed; PAUSED is never public.
- flatRentalMode=ENTIRE_FLAT|ROOM restricts results to FLAT; explicit PG_HOSTEL conflicts. Room-count/gender-room/sharing filters exclude ENTIRE_FLAT and conflict with that explicit mode. Whole-flat vacancy uses status/wholeFlatAvailable, not room totals.
- Geo search requires lat+lng+radiusKm together, 0 < radiusKm <= 100; validate coordinates against documented coarse bounds, not a strict India boundary, plus all ranges/types/enums. Invalid/unknown parameters -> 400; no silent truncation. Totals use identical visibility and filter predicates as items; see `docs/LISTING_SEARCH.md`.
- `GET /api/v1/listings/{id}`: public for ACTIVE/FULL_OCCUPIED; public responses exclude owner phone, private address, and precise coordinates. Map coordinates require the documented coarsening policy in `docs/LISTING_SEARCH.md`, otherwise omit them. PAUSED visible only to its authenticated owner, with a no-store response, otherwise 404.
- `POST /api/v1/listings`: authenticated account creates a PAUSED draft and becomes its owner; normalized city, immutable category/flatRentalMode and mode-appropriate inventory required. No city default. Photos and verified contact checked at publication; return 201 with id/version. Full model: `docs/LISTING_MODEL.md`.
- `POST /api/v1/listings/{id}/publish`: owner only, {version}; require verified +91 contact, category-required VALIDATED photos, valid inventory, and serialized five-listing quota. PAUSED -> ACTIVE if ENTIRE_FLAT wholeFlatAvailable=true or ROOM/PG total > 0, otherwise FULL_OCCUPIED; return listing/version.
- `POST /api/v1/listings/{id}/pause`: owner only, {version}; set PAUSED and release its quota slot, preserving content; return listing/version. Stale versions -> 409; no reports/ratings may trigger this action automatically.
- ListingResponseDto includes category, flatRentalMode (NULL for PG), applicable inventory, monthlyRent, currency=INR, rentPeriod=MONTH; rentBasis=PER_PERSON for PG, PER_PROPERTY for ENTIRE_FLAT, PER_ROOM for FLAT ROOM. Deposit uses the same basis; quoted rent filters/sorts never convert it.
- `PATCH /api/v1/listings/{id}/inventory`: owner only; ENTIRE_FLAT accepts {wholeFlatAvailable, maxOccupants, version}; ROOM/PG accepts {maleRoomsAvailable, femaleRoomsAvailable, sharedRoomsAvailable, maxSharingPerRoom, version}. Reject inapplicable fields, mode/category/status/client totals.
- Owner sets positive-integer maxOccupants for ENTIRE_FLAT (people per flat), or maxSharingPerRoom in 1..10 for ROOM/PG (people per room), at creation/update. Return applicable capacity on search/detail/owner DTOs; other capacity field is NULL. Capacity never multiplies quoted rent or implies current occupancy.
- Inventory response includes applicable availability, computed status, version; ENTIRE_FLAT totalRoomsAvailable=NULL. PAUSED remains PAUSED; only explicit publication can reactivate it.
- Check version before every inventory/publish/pause write; stale -> 409 even on retries. Current-version publish/pause already in target publication state is a no-op with unchanged version/quota. Accepted inventory updates increment version. Brokerage-report retry rules remain separate.
- `POST /api/v1/listings/{id}/images/presign`: owner only, for an existing listing/draft; bounded segment/type/size request -> {imageId, objectKey, uploadUrl, expiresAt}; reserve a PENDING image and a short-lived staging-object PUT URL.
- `POST /api/v1/listings/{id}/images/complete`: owner only, {imageId}; verify upload ownership, actual content/type/size and storage immutability, then mark VALIDATED and return image metadata. Same validated image is idempotent; pending/rejected images never satisfy publication requirements.
- `POST /api/v1/interactions/listings/{id}/reveal-phone`: authenticated; returns authorized verified +91 contact and wa.me link for a published listing; no-store. Sandbox contact actions are disabled and return no callable contact data.
- Reveals: 10 distinct listings/user/Asia-Kolkata day; same listing/day is idempotent; own listing reveal disallowed.
- Review identity: immutable UUID with unique `(reviewer_id, property_id)` per database, regardless of report flag; reviewer comes from authentication and owner from the property, never request-supplied IDs.
- Prior revealer means a historical contact_reveals row for the same authenticated user, listing, and owner, on any date; no same-day review deadline. Listing ownership is immutable.
- `POST /api/v1/interactions/listings/{id}/report-brokerage`: authenticated prior revealer, no self-report; creates the pair's review if absent or converts that same row in place to rating=1, issue_tag=ASKED_BROKERAGE, is_auto_broker_report=true.
- Conversion preserves review UUID, created_at, and existing comment_text; a newly created report uses the automated allegation text. Display the report notice separately from preserved user text.
- Repeated brokerage reports return the existing review without changing content or aggregates; never create a second review or modify another reviewer/property pair.
- All review/report writes serialize on the owner row; review mutation and owner average_rating/review_count/broker_report_count updates commit or roll back in one transaction. A conversion does not increment review_count; retries do not increment any count.
- `POST /api/v1/interactions/listings/{id}/reviews`: authenticated prior revealer; {rating, issueTag, commentText}; create-only, no self-review; an existing pair returns 409 without mutation. ASKED_BROKERAGE must use the report endpoint; ordinary reviews cannot clear a report.
- Public reports are allegations; never automatically hide/suspend listings.
- Sandbox persona/reset/telemetry APIs exist only on a separately configured sandbox backend, with bounded privileges.
- `X-Sandbox-Mode` never selects a database or grants authorization; production rejects sandbox sessions/tokens and cannot read the sandbox session store.
- Phase 1.8 adds container-only tests for header/store isolation, server credential rejection, production handler absence, and real dependency failures through test-only probes. No probe is packaged. Docker is unavailable locally, so the suite's required setup fails and actual isolation remains unverified; `docs/BACKEND_ISOLATION.md`. Session/token isolation awaits Phase 2; no business route added.
- Sandbox responses and all personalized/contact/auth responses use no-store and bypass shared caches. Only unauthenticated production listing responses may enter a shared cache.
- Public listing caches must be partitioned by deployment; rating/report, listing/status, and inventory writes invalidate affected cached views.
- Phase 1.7 common errors implemented as application/problem+json: type=about:blank, standard title, numeric status, fixed safe detail, instance=urn:uuid:<server ID>; X-Error-Id matches, Cache-Control=no-store. No request path/query, exception text, validation values, contacts, SQL, or tokens. `docs/BACKEND_HTTP_ERRORS.md`.
- Recognized malformed/validated input 400, authentication 401, access denial 403, absent resource 404, unique/stale conflicts 409, explicit quota/rate condition 429, known infrastructure outage 503; unexpected failures generic 500. Generic integrity/FK/schema/application bugs are not mislabeled 409/503. Future services still implement contact/publication/quota gates; a sixth publication will be 409.
